### Prototype

**You own the design decision. The prototype is a throwaway instrument; the real build follows Feature.**

1. Choose the route from the requested outcome. UI wireframes, page layouts, product flows, and 原型图 use the **UI canvas** route. Nonvisual questions about behavior, timing, or an implementation approach use the **Empirical probe** route. Follow only the route needed for that question. A request for 原型图 already establishes a deliverable; do not require the user to invent a competing design first.
2. Build through the selected route:
   - **UI canvas.** Read and follow the standalone [prototype skill](../../prototype/SKILL.md) end to end, including its canvas UI reference and explicit user-approved exceptions. Carry in the requested page scope, supplied references, repo design rules, and earlier approvals. The deliverable is one editable, navigable canvas with the different pages visible together as separate artboards. Preserve the reference UI outside the page interiors with pixel-level alignment, except for changes the user explicitly requested; customize the page contents. Keep alternative designs in labeled groups on that canvas when comparison is requested. The skill owns the template, layout, and interaction details.
   - **Empirical probe.** State the concrete question, the conditions to reproduce it, and the observation that would distinguish the approaches. Read the relevant project constraints and run the smallest probe in an isolated scratch directory. Accumulate rounds in sibling topic-dated directories without overwriting earlier work. Keep the probe scoped to the question; it needs neither a UI canvas nor production scaffolding.
3. Verify the actual artifact on the matching surface. For UI work, follow the skill's overview, page readability, canvas navigation, and main-path interaction checks. When changing the canvas UI, also run its fixed-baseline screenshot comparison with page interiors and named user-approved exceptions excluded. Check each approved change separately. A nonzero difference elsewhere is not pixel-exact. Deliver the editable canvas alongside any screenshots. For a nonvisual probe, capture the observed output or timing with the command and conditions that produced it. Report any verification limitation explicitly.
4. Iterate without losing approvals. Preserve confirmed pages, states, features, and variants in each later round unless the user drops them. Present tradeoffs and a recommendation when a choice remains; a single requested direction does not require invented alternatives.
5. Finish at the requested scope. If another playbook called this one to settle a question, return the artifact and findings to that caller. When the user asks to implement the approved direction, carry the chosen pages, states, interactions, and decisions into **Feature** (or `architect` for the shape), then stop extending the prototype. Update the project's decisions/features record if it has one.

**Reply:** link the editable canvas and name its pages and mocked interactions for UI work, or link the probe and give its command and observed results for nonvisual work. Include the scratch path, verification evidence or limitations, any open decision, and tradeoffs or a recommendation when relevant. Say plainly that the code is disposable.
